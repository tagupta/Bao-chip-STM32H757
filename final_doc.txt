Secure Firmware (updated Oct 2026 - holodi-fc)

We create a root secret on HoloDi (holodi-fc keys gen) — this generates three derived keys: link, pairing, firmware
We export the firmware and pairing public keys from HoloDi (holodi-fc keys)
We modify the bootloader of the FC and embed TWO public keys: firmware in slot 0, pairing in slot 1
We prepare a firmware for the FC on my laptop
We send only a 64-byte digest to HoloDi for signing (holodi-fc fwsign begin/finish)
We then get the signed firmware from HoloDi to our laptop
We then flash the firmware and the signature generated by HoloDi to the FC directly from our laptop
FC should accept/reject bootloading if the signature is valid/invalid.
The build now refuses an image whose embedded bootloader doesn't trust its signing key (Cube safety).

Q1 What stops an attacker from replacing the public key with another one?

A1: In the dev mode for FC, this can't be prevented. Assumption is that you can block these memory locations at the setup phase at the factory-level so the underlying key can't be replaced.

The private key would then sit in the HoloDi.

Only authenticated commands are obeyed by FC (frame version 3 — replay-safe):

1. Set up a root secret on baochip (holodi-fc keys gen). Three keys derive from it.
2. Both public keys (firmware + pairing) are loaded in the bootloader (two slots).
3. Any command from the ground (ie laptop) needs to be signed by HoloDi's private key from step 1 
4. FC' firmware checks if the signature on the command is valid and only then it processes the command.
5. Commands are bound to the FC's boot — a recorded command can't be replayed after a reboot.
